# ADR-5: Filesystem checkpointer and durability tiers

**Decision:** Run state is checkpointed to `.bober/checkpoints/<runId>/<superstep>.json` by a `FsCheckpointer` constructed per invocation with `projectRoot` as a required argument, written temp-file-plus-rename, with `durability: "exit" | "superstep"` configurable and `"superstep"` proposed as the default. These paths are added to `.gitignore`.

**Context:** Resume must survive process exit, because the human-in-the-loop round trip spans separate CLI invocations — which is why `src/orchestrator/checkpoints/mechanisms/disk.ts` already exists. The source documents prescribe `MemorySaver()`, and every persistent checkpointer published for LangGraph is a database (`@langchain/langgraph-checkpoint-sqlite` 1.0.3 requiring the native `better-sqlite3`, `-postgres` 1.0.4, `-redis` 1.0.10, `-mongodb` 1.4.0).

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| **A. In-process checkpointer (`MemorySaver` equivalent)** | Zero I/O cost; no format to version; no on-disk cleanup | State dies with the process, so an interrupt raised in one CLI invocation cannot be resumed by the next — the exact HITL round trip the design must support. Also loses all crash recovery |
| **B. Embedded SQLite via `better-sqlite3`** | Already a repo dependency; precedent exists in `src/state/facts.ts` and `src/fleet/shared-blackboard.ts`; indexed lookup and transactional writes | Checkpoints become opaque to `cat`, `git diff` and hand inspection, which is the debugging affordance the whole trace/replay goal depends on; a native module adds install-time build risk for a CLI symlinked into arbitrary projects; unnecessary until lookup cost dominates, and lookup is one file per superstep by known key |
| **C. Filesystem JSON checkpointer (selected)** | Satisfies "no database, no service the user must run" literally; a checkpoint is human-readable and diffable; temp-file-plus-rename gives atomicity without a transaction manager; `projectRoot` as a constructor argument keeps worktree runs isolated | Every checkpoint is a separate file, so a long run leaves many small files requiring retention pruning; concurrent writers would need coordination (avoided because `CommitBoundary` is the single writer) |

**Rationale:** The **success criterion "a run killed after node 3 and restarted in a fresh process re-invokes zero of nodes 1–3 and yields the uninterrupted run's artifact"** eliminates Option A outright — it is unsatisfiable by any in-process store, which is exactly why it was chosen as the discriminating test. Option B is eliminated by the **Locked Dependency "Filesystem-only state under `.bober/`"** read together with the debugging goal: the design's value rests on a run being inspectable after the fact, and an opaque binary store removes that for the one artifact that records where a run stopped. Option B remains the sanctioned escalation if measured lookup cost ever dominates, since the principle's intent is "no service the user must run" rather than "no persistence".

**Consequences:** `Checkpoint` carries `state`, `pending`, `completedTaskKeys`, an optional `InterruptRecord`, and `graphId`/`graphVersion`/`checksum`; `resume` throws `ChecksumMismatch` rather than replaying task keys against a changed graph. Resume skips dispatch of any `taskKey` in `completedTaskKeys` — `sha256(nodeId + branchKey + inputHash)` — generalising the skip-before-dispatch discipline at `resume-cursor.ts:12` from sprint numbers to task keys. `CompiledGraph` has no checkpointer field, so a subgraph owning its own persistence handle is unrepresentable (`subgraphs[].persistence` is `z.literal("inherit")`, and `NestedCheckpointer` covers hand-edited JSON). `.gitignore` gains `.bober/checkpoints/`, `.bober/scratch/`, `.bober/traces/`, `.bober/cache/`, `.bober/archive/` and `.bober/logs/`; without this a 40-node run commits ~40 files into a tree already tracking 1,224 files under `.bober/`, where `.gitignore` excludes only `snapshots/`, `medical/`, `chat/`, `memory/*.db` and `graph/.hook-queue.jsonl`.

**Risk:** A bug in checkpoint write ordering or in `completedTaskKeys` reconstruction re-executes a completed node or skips an incomplete one — both silent. The only defence is an adversarial conformance suite over `put`/`get`/`list`/`prune` modelled on the published `@langchain/langgraph-checkpoint-validation` contract (https://registry.npmjs.org/@langchain/langgraph-checkpoint-validation), with kill-mid-write fault injection asserting no partially written checkpoint is ever readable.
