# ADR-8: TypeScript engine migration and conditional retirement

**Decision:** `PgeEngine` ships as a fifth `PipelineEngineName` behind the private engine seam with `pipeline.engine` defaulting to `"ts"`; `TsPipelineEngine` is retained **permanently** as the conformance oracle and is not scheduled for deletion; the dormant `src/orchestrator/workflow/` subtree is deleted only after its assertions are green on the graph runtime and `ts`-vs-`pge` conformance is a blocking CI job. If conformance never goes green, PGE remains a permanently opt-in engine and nothing is removed.

**Context:** Two engines cannot both be "the semantics" without a mechanical way to prove they agree. `EngineConformanceHarness` (`conformance.ts:64-153`) was built for exactly this and has never been pointed at a real engine — its only non-self reference is its own test. The repo also carries a cautionary precedent: `src/orchestrator/workflow/` is fully built with 189 green tests yet unreachable, because `eligibility.ts:10-11` returns a hardcoded `false` and `workflow-engine.ts:90-94` throws unconditionally.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| **A. Replace `runTsPipeline` in place** | One engine, no dual maintenance, no divergence surface; the fastest route to a single code path | No oracle: after deletion every conformance failure reads as "something changed somewhere" rather than "the graph engine regressed"; the frozen `PipelineResult` shape and the terminal side-effect set would be re-derived from 1,068 orchestrator assertions rather than compared against a working implementation |
| **B. Parallel engine, default-off, delete the TS engine after N green releases** | Reversible during the transition; a scheduled end state avoids indefinite dual maintenance | The deletion date is set before the evidence exists; if conformance stalls the plan has no sanctioned resting place and the repo straddles two engines with no decision recorded |
| **C. Parallel engine, default-off, TS engine retained indefinitely with a pre-authorised terminal fallback (selected)** | The oracle survives, so every future conformance failure has a single interpretation; a stalled migration has a named, shippable end state rather than an open question; the topology layer retains full value (G1/G2/G4) even if the runtime is never defaulted | Two engines are maintained for as long as both have users, which is a real ongoing tax; the "conditional" deletion may become "never" by default rather than by decision |

**Rationale:** The **Backward-compatibility constraint** — `runPipeline`'s signature frozen at `pipeline.ts:1074`, `PipelineResult`'s field set frozen at `pipeline.ts:66`, and the `pipeline-complete` event plus `.completed.json` marker required identically from every engine or `src/chat/completion-tailer.ts:181` hangs — eliminates Option A: without a running reference implementation there is no mechanical way to demonstrate those three invariants hold, and the coupling at `completion-tailer.ts:181` is an untyped string-literal match that no type error and no existing test outside that module would catch. Option B is eliminated by the same dormant-subtree evidence cited in Context: a migration whose only defined outcome is completion produces an unreachable half-finished layer when it stalls. The terminal fallback in Option C is grafted from a runner-up design at the panel's recommendation.

**Consequences:** `finalizePipelineRun` is extracted from `pipeline.ts:1015-1054` and called by `TsPipelineEngine`, `RunResultFlusher` and `CommitBoundary.finalize`, with `PIPELINE_COMPLETE_EVENT` and `COMPLETION_MARKER_SUFFIX` exported as constants imported by both producer and consumer — this also repairs the pre-existing divergence in which `flusher.ts:34-104` writes neither the marker nor the terminal event. `EngineConformanceHarness` gains a real `runnerFor` (deterministic client, frozen clock, fixed runId), a widened 11-field artifact set, and an order-tolerant structured diff. `PgeEngine` mirrors `selector.ts:29-31`: on `TopologyCompileError` it logs one downgrade line and re-dispatches `TsPipelineEngine`. `Scheduler`, `Semaphore`, `mapBounded`, `Budget`, `retry.ts`, `reconciler.ts`, `synthesizer.ts` and `conformance.ts` are retained permanently and gain their first production callers.

**Risk:** `bober sprint` (`cli/commands/sprint.ts:144-310`) and `bober_sprint` (`mcp/tools/sprint.ts:163-289`) each re-implement the sprint loop without the security, curator, review or documenter stages, so any claim about "the engine's semantics" is false for two of three entry points. If that divergence is not explicitly resolved — re-pointed or formally deprecated — before the sprint subgraph ships, this decision widens a latent correctness gap rather than closing it.
