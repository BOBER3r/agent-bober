# ADR-4: State schema split and batch-signature reducer strategy

**Decision:** Split state into `OverallState` (14 public Zod keys, snapshot-pinned), per-node input/output port schemas resolved from `src/contracts/`, and `NodeContext.priv` (node-local, never a channel). Fan-in uses a closed registry of six reducers whose signature is `merge(current: T, updates: readonly T[]): T` — called exactly once per channel per superstep with the whole batch — and each declares `associative`, `batchingInvariant`, `orderInvariant` and `idempotent` as literal `true`.

**Context:** Concurrent branches write the same channels. R33 asks for associative and batching-invariant merging; R37 asks that each state key be written exactly once and that concurrent output be byte-identical to sequential output. Associativity alone does not deliver either once a superstep can be replayed after a crash or an interrupt resume.

**Options Considered:**

| Option | Pros | Cons |
|--------|------|------|
| **A. Pairwise-fold reducers** (`operator.add` / `add_messages` style, folded update-by-update) | Matches the reference framework idiom directly; trivially composable; smallest interface | Associative but *not* order-invariant: two branches finishing in a different order yield different arrays, so concurrency-1 and concurrency-8 runs diverge. Batching-invariance is an emergent property of each implementation rather than a testable law — nothing in the signature prevents a reducer from observing interleaving. Not idempotent: a replayed superstep double-appends and double-counts loop counters |
| **B. Last-writer-wins per channel** | Simplest possible merge; no reducer registry at all | Loses concurrent branch results outright; makes `messages` and `evaluations` lossy; the whole fan-in barrier becomes meaningless |
| **C. Batch-signature join-semilattice reducers (selected)** | Batching-invariance is directly testable — `merge(merge(s,xs),ys) === merge(s,[...xs,...ys])` is an assertion over the actual signature; exactly-once-per-channel writing is true by construction because the reducer is invoked once per superstep; idempotence makes crash-replay and interrupt-resume safe; order-invariance makes concurrency-1 and concurrency-8 byte-identical | Only six reducers exist and they are closed — a node needing a bespoke merge must either fit one or extend the registry deliberately; the four literal-`true` flags are a discipline the type system enforces but cannot prove |

**Rationale:** The **success criterion "the same golden spec at concurrency 1 and concurrency 8 produces byte-identical `.bober/` artifacts"** eliminates Option A: plain append is associative yet order-dependent, so that criterion — and with it the `EngineConformanceHarness` comparison and offline trace replay (R62) — becomes non-deterministic and the CI gate flaky rather than decidable. Option A is further eliminated by the **Constraint that a run killed after node 3 and restarted in a fresh process must yield the uninterrupted run's artifact**: a non-idempotent counter reducer over-counts on replay, so a bounded loop can exhaust early or never. Option B is eliminated by R34/R45, which require the evaluator to observe exactly N branch results with successful branches preserved. This strengthening is grafted from a runner-up design at the panel's recommendation.

**Consequences:** `Reducer<T>` carries four literal-`true` flags, so a reducer that is not a join-semilattice is unregisterable at the type level. Bindings: `appendById` (union by intrinsic id, sorted by `(seq,id)`) for `messages`/`evaluations`/`refs`; `maxNumber` for `counters`; `lastWriteWinsByKey` over disjoint per-branch keys for `branchStatus`; `setUnion` for `testAnchors`; `replaceIfNewer` for the single-writer `spec` channel; `mergeLedger` keyed `(nodeId, attempt, callIndex)` so a re-executed call replaces rather than adds. `NonAssociativeReducerUnderFanOut` and `MultipleWritersOnScalarChannel` are validator errors. Channel `writers`/`readers` are **derived** from `nodes[].writes/reads` and never stored on `channels[]`, so the state audit (R73) has a single encoding to read; `ChannelDeclMismatch` guards the one remaining cross-reference.

**Risk:** If a future channel needs a merge that is genuinely order-dependent (for example a true event log where arrival order carries meaning), no registered reducer fits and the byte-identical criterion cannot hold for it. That channel must instead be modelled as an offloaded artifact referenced by `refs`, or the criterion must be explicitly relaxed for it in the same commit.
